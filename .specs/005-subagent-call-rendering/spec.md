# Specification: Subagent Call and Output Rendering

## Behavior

- **S1:** A live pending call renders an animated `<spinner> Agent Call · <agent> · background · <new|resume>` row, or `<spinner> Agent Call · <agent> · steer` for the immediate steer control operation (steer carries no execution-mode label). Expansion shows the sanitized prompt. An accepted queued/steer call settles to `» Agent Call ...`. A tool-level failure before queued/steer acceptance (schema/runtime error envelope such as `MODEL_NOT_FOUND`, `THINKING_LEVEL_UNSUPPORTED`, `INVALID_ARGUMENT`, or `SESSION_NOT_FOUND`) settles to the literal lowercase ASCII `x Agent Call ...` with the available agent identity; the heading carries only glyph/title/metadata, never an inline error suffix. A later background child failure never changes Agent Call: once queued was accepted, the row remains `»`.
- **S2:** Final `renderResult` stops spinner state and synchronizes durable agent identity. It returns an empty component for success; for a tool-level failure it returns an indented one-line error-reason body that is visible even when collapsed. The expanded prompt (if any) still renders in the call row above the reason. The tool execution box contains only `Agent Call` plus, on failure, its reason.
- **S3:** There is no foreground execution and no foreground Agent Output entry. `new`/`resume` tool results carry only the queued background acceptance; steer results carry only the running acknowledgement. No custom entry is appended at `turn_end` or any other lifecycle event.
- **S4:** Removed (foreground entries no longer exist). Hidden completion signals remain fully present in model context.
- **S5:** Fetched `subagent_output` results render in that tool's result region as: collapsed `« Agent Output · <agent>` or literal lowercase ASCII `x Agent Output · <agent>`. Failure headings carry only glyph/title/metadata, never an inline error suffix. The failure glyph applies to retrieval errors and to retrieved terminal results indicating failure/error (`failed`, `aborted`, `stopped`, or an `error` field/envelope); `completed` (and other non-failure statuses without an error) stays `«`. Every failure shows an indented one-line error-reason body even when collapsed: the safe error message/code when usable, else the terminal failure status, else a generic safe label. The reason is sanitized (ANSI/control stripped, single-line) and capped at 120 characters. When expanded, actual output (including useful partial output when an error is also present) is preserved alongside the still-visible reason, and byte-identical error text is not duplicated. Standalone error bodies are independently sanitized and capped at 100,000 characters so a huge error is not displayed without bounds. For the current failed assistant-stop result only, expanded output also shows nonempty sanitized provider error text from volatile memory; it never appears in collapsed output or tool data, and aborted results do not show it. Pi's HTML `/export` reuses this expanded renderer and can save that provider text into HTML. Malformed and error envelopes render safely without throwing.
- **S6:** Background completion delivery is the hidden custom signal sent with `{ triggerTurn: true, deliverAs: "followUp" }` and `display: false`, preserving exactly-once delivery and immediate follow-up reaction. No toast is shown, no completion message renderer is registered, and no custom entry is appended for background queued acceptance or later completion.
- **S7:** Model-facing final result `content` remains the exact serialization of the unchanged service result. Host-persisted details may add only typed, namespaced agent presentation metadata.
- **S8:** Actual resume/steer identity is synchronized from lifecycle callbacks, final details, or namespaced presentation metadata. Background `new`/`resume` identification updates presentation metadata only and never emits a partial `onUpdate`.
- **S9:** Spinner timers are unref'd and stopped on replacement, invalidation failure, and final success/error. Replay/export isolation does not mutate a live spinner sharing the tool call ID.
- **S10:** The standalone HTML exporter does not invoke custom message renderers, so background custom messages export generically. Nested tool output is not restored as an HTML workaround. The exporter snapshots the `subagent_call` header before the result is known (its `renderCall` receives no error context), so for a failed call the exported header may read `»` while the failure glyph and reason are carried by the exported result section; interactive replay shows the settled `x` heading plus reason correctly. Export determinism is claimed only for the result section, not the failed-call header.

## Acceptance Criteria

- **A1:** Tool rendering tests prove background pending/accepted behavior, steer control rendering without an execution-mode label, prompt expansion, identity synchronization, timer cleanup, heading-only failure rows with an always-visible sanitized/capped reason body (including status-agnostic call fallbacks), prompt/reason coexistence when expanded, empty final `renderResult` for success, and interactive replay of failures with heading plus reason.
- **A2:** Lifecycle tests prove no custom entry is appended at any lifecycle event, no `sendMessage` fires from call rendering, no message renderer is registered, and unchanged hidden background delivery.
- **A3:** Tool result renderer tests prove exact collapsed and expanded success (`«`, body only when expanded) and failure (`x`, heading-only plus always-visible reason) rows inside the `subagent_output` result region, terminal `failed`/`aborted`/`stopped`/error-field failure detection, the 120-character reason bound, partial-output-over-error priority with the reason kept visible, no duplicate identical error text when expanded, sanitization, safe malformed/error envelopes with code/status/generic fallbacks, and the 100,000-character expanded-body cap, and provider error text only for the current failed assistant-stop result when expanded (including resume/reload invalidation, empty-text omission, and carriage-return sanitization).
- **A4:** Replay/context tests prove hidden completion model-context presence, HTML tests document generic custom-message export, and export tests prove the failed-call reason is present in the exported result section while documenting that the exported call header may stay `»` (host snapshots the header before the result is known).
